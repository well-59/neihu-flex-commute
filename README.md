# 內科錯峰效益模擬器

平日晨峰，誰移？移多少？省下的時間歸誰？

目標是用臺北市 VD 實測資料校準內湖晨峰模擬器，協助市府與企業討論分批上班、彈性工時。目前尚未完成校準。
題目來源：市政 debug 松 issue #4「內湖尖峰車流好比停車場」。

> **2026-10-21 本機整合：** 企業試算仍使用虛構樣本；新增的實測依據來自 2025 年官方路口調查。兩者分開呈現，沒有把路口通過量直接當作模型抵達需求。10/22、10/23 的 VD 收集是計畫，尚未取得，資料處理與校準程式尚未完成。

## 真實資料／模擬資料

| 資料 | 來源 | 性質 |
|---|---|---|
| 六個路口、15 分鐘分車種通過量 | 交工處 2025 年原始 XLSX | 已取得；6/24 與 9/11 兩日樣本，07:00–09:00，09:00–09:30 缺測 |
| VD 每分鐘流量、速度、佔有率 | 臺北市即時交通資訊 `VDLive.xml` | 計畫收集；目前頁面為虛構樣本 |
| 路段旅行時間 | 臺北市即時交通資訊 `LiveTraffic.xml` | 計畫收集；尚未接入畫面 |
| 路徑旅行時間（各出發時段） | 目標為 Google Routes API | 目前為自訂樣本，尚未呼叫 API |
| 4 種公司類型的人數、開車比例、上班時間 | 自訂 | **模擬** |
| 背景需求拆分、排隊延滯 | Point queue 模型推算 | 推算 |

本專案不使用任何真實個資，4 種公司類型均為匿名的虛構樣板。

## 結構

```
collector/   每分鐘抓取 VDLive / LiveTraffic（Node，無外部套件）
scripts/     資料處理；make-sample-data.mjs 產生樣本資料
web/         單一頁面儀表板（index.html + data/neihu-data.js）
web/evidence/ 官方路口調查 Dashboard、原始 XLSX、重建程式與既有測試
archive/     本機準備文件、參考版、早期原型與歷史截圖（非現行入口）
DESIGN.md    設計稿
```

本機預覽：直接用瀏覽器開啟 `web/index.html`。
可用網址參數預設情境，例如 `?arch=A&pct=30&shift=60`；另支援 gate、mode、theme。設計中的 rebound 與 view 尚未實作。

首頁「查看實測圖表」連到 `web/evidence/index.html`；實測頁可返回新版試算。離線單檔為 `web/evidence/neihu-dashboard-v2.html`。
整合來源、差異與待辦見 [INTEGRATION.md](INTEGRATION.md)。原版資料夾保留。

資料對帳：`python3 web/evidence/data/build.py`。
資料／模型測試：`node --test web/evidence/tests/data-model.test.cjs`。
重新產生實測單檔：`python3 web/evidence/build-standalone.py`。

手動收集：`node collector/collect.mjs --start 06:45 --end 10:30`（主機時區須為 Asia/Taipei，需保持開機與連線）。本次未啟動收集或排程。

## 模型限制

- 每個通勤口視為獨立的單一瓶頸，不含下游回堵與通勤口之間的互相影響。
- 真實 VD 的兩日收集尚未完成；既有 2025 調查也不能代表現今長期平均。
- 未建模 capacity drop；偏差方向與幅度尚未驗證。
- 企業人數轉成車次包含一人一車假設，不能直接當成全體員工通勤效益。
- 各通勤口的效益只適用獨立模型，未確認路徑重疊前不可加總成全內湖效益。

## 市府 100 天落地（PROPOSED）

1. 第 1–30 天：交通局開放 VD 歷史序列，建立每 15 分鐘的晨峰基準線。
2. 第 31–60 天：邀 3–5 家內科企業試辦分批上班，以匿名問卷取得通勤方式與路線。
3. 第 61–90 天：試辦期間每天比對基準線，公開儀表板。
4. 第 91–100 天：公布成效，結果納入企業 ESG 揭露與後續獎勵機制。
