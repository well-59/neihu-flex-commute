## 1. 總覽八項 KPI（`App.jsx:290-297`）

FACT：
- **日期範圍固定**：總覽一律用全部可用日期，共 21/22 日（`App.jsx:612`），不會跟著「車流觀測」頁的日期選單變。
- **假日一律計入**：3 個國定假日都算在內（`ranking.mjs:28`；`aggregate.mjs:277` 只篩到 requestedDates）。只有星期圖可以切換排除。
- **我方預設口徑相反**：我方預設排除假日（`route-evidence-model.js:24`），所以同名指標在兩邊的數字會不同。另外 `route-evidence.js:13` 寫死「3 個國定假日」：如果使用者選了某個假日當單日、又勾了排除假日，就會出現 0 日，但文案仍顯示「所選日期均有快照」。

各項 KPI 的問題：

| KPI | 分母與問題 |
|---|---|
| ① 分析工作日 | 21 日；缺的 09/24 只寫在 coverage 裡 |
| ② 往園區路段 | 數的是有分級分鐘的列數 `rows.length`（`dashboard.mjs:23`），附註卻寫 inScope 的 31 個方向，兩個口徑不同 |
| ③ 整體塞車比例 | 所有路段的 E/F 分鐘合計 ÷ 已分級分鐘合計。已分級分鐘越多的路段影響越大；5 分鐘內都沒車的分鐘不在分母裡 |
| ④ 最塞 15 分鐘 | 同樣是合併計算，同分時取最早的時段 |
| ⑤ 最塞路段、⑥ 流量最高 | 沒有最低樣本門檻（`ranking.mjs:227-229,248-250`）。反例：某路段只有 3 個已分級分鐘、全是 E 級，就會以 100% 排第一 |
| ⑦ 與官方等級相同 | 樣本包含所有有官方路段的內湖方向，也就是出園、園區外的路段（`aggregate.mjs:263-271`），和另外七項只看往園區路段的範圍不同 |
| ⑧ 完整度 | 分子是全部代表方向的有效分鐘（`dashboard.mjs:44`），分母是 `rows.length×150×21`（`App.jsx:297`），兩邊集合不同。分母用 21 日而不是 22 日，所以缺漏的 09/24 不會被扣分 |

## 2. 壅塞地圖

FACT：
- **線形是官方的**：用的是官方 LinkID 線形，座標四捨五入到 1e-5（`aggregate.mjs:86`），可以直接疊到我方地圖。
- **看不出方向**：熱度圖模式沒有方向箭頭（`App.jsx:93` 的 heat 分支沒有 markerEnd）。雙向道路兩個方向的線形重疊，顏色也互相覆蓋，看不出是哪個方向在塞。
- **顏色是整期累計比例**：顏色代表全期間 E/F 分鐘的比例，不是任何一個時刻的現況。
- **速度的意義**：先把各車道的 Speed 依車次加權，再取 5 分鐘尾隨平均（`ranking.mjs:91-93,135-145`）。這是偵測器所在那一點的速度，隊友自己也寫了它不是整段路的旅行時間（`App.jsx:489`）。
- **門檻組別有時間錯位**：發布路段用哪組壅塞門檻，取自下載參考資料當下那一刻的即時快照（`reference.mjs:139,151`），卻被套用到所有歷史日期。
- **沒有官方路段的巷道**：用道路分類的預設門檻（`aggregate.mjs:84`）。

可以接進我方的：LinkID 線形、類別（entering/internal）、sectionId、比例和對應的分母。

不能當成的東西：現場即時路況、整段或整條路線的速度或旅行時間、道路容量。

## 3. 彈性上班推論

可以延續的（FACT）：
- 品質篩選和 5 分鐘速度算法
- 每 15 分鐘時段的分母
- 列出「幾天過半塞車」（`flex.mjs:62`）
- 有官方路段可對照的標示

需要修正的（PROPOSED），附反例：
1. **基準路段選法**（`flex.mjs:57`）：優先挑「有官方路段」的，不是挑最塞的。反例：A 路段塞 80% 但沒有官方路段，B 路段塞 10% 但有官方路段，結果用 B 當基準，建議時間被低估。
2. **塞車解除時間**（`flex.mjs:67`）：取的是「最後一個」塞車時段，即使中間不連續。反例：07:15 和 09:00 兩段塞車、中間都順暢，解除時間仍算成 09:15。
3. **沒有考慮行車時間**（`flex.mjs:68`）：直接拿路段塞車的時鐘和到班時間比較。反例：上班 08:30、基準路段 07:45–08:15 塞車，判定不需延後；但 08:30 要到班的員工大約 08:10 會經過該路段，正好在塞車中。
4. **因果話術沒有模型支撐**（`App.jsx:394-395`）：「延到塞車解除就不會遲到」這種說法，沒有考慮大家一起延後時塞車也會跟著往後移。在沒有模型之前，我方應維持 `policyEffect:null`。
5. **方向判定不是路徑**（`flex.mjs:43`）：用「中點方位」加「終點比起點更靠近公司」來分方向，屬於幾何推估，不是員工實際走的路，經過公司附近的過境車流也會被算進去。
6. **即時規則**（`flex.mjs:85-89`）：最多只延到 t+15。發布本身就有延遲（見第 4 節），使用者看到時，這個時間可能已經過了。

**新版建議順序**：先做全路段的整體分析（時段熱圖、排名、完整度），再讓使用者輸入地點，系統列出候選路段的證據供參考，不直接輸出「建議最晚上班時間」。

## 4. 汽機車資料與即時化缺口

FACT：
- **源頭有分車種**：原始資料每個車道都有 `Vehicles[]` 的 S/M/L/T 四種車，而且每種都有自己的 Volume 和 Speed（`dashboard.json:284984-284986`）。
- **處理時就合併了**：流量把所有車種直接相加（`ranking.mjs:88`），速度只用車道層級的 Speed（`:92`），各車種的 Speed 被丟掉（`:89`）。
- **快照只剩一分鐘的樣本**：每個方向每天只保留一分鐘的 laneVolumes 當例子（`aggregate.mjs:224`）。我方匯入時連這個例子也刪了（`import-route-clarity.mjs:16`），同時刪掉了 `receivedMinutes` 和 `reasonCounts`。後果是：「個別路段檢查」分不出「沒收到」和「品質沒過」兩種缺漏，也看不到排除原因。
- **live 輸出沒有流量**：`live.json` 的 segments 不含流量也不含車種（`live-update.mjs:80`），而且每次執行都覆寫成最新一份（`:103`；`pages.yml:57-62` 只快取最新的 live.json），所以沒有即時資料的歷史可回放。
- **發布延遲**：每次執行要先輪詢 15 分鐘，之後才 build 和部署（`pages.yml:22-24`），前端再每 5 分鐘抓一次（`App.jsx:249`）。頁面上判定「新鮮」的條件是 30 分鐘內（`live.mjs:14`）。換句話說，標成「即時」的資料實際上大約落後 15–30 分鐘以上。
- **即時建議仍用歷史日期**：即時的公司建議仍拿含假日的歷史日期當基準（`live-update.mjs:84`）。

UNKNOWN：
- M 代表機車，是依 TDX 慣例推定，需要到 TDX 文件核對。
- 機車在混合車道是否被偵測器完整計數，沒有驗證。
- 外部 API 的配額和延遲，這次沒有驗證。

真正還缺的：
1. 分車種的逐分鐘聚合，和可回放的即時資料存檔
2. 每筆資料帶「資料時間、取得時間、發布時間」三個時間戳，前端依此分級顯示為即時、近即時或歷史
3. 多個 VD 來源（市區、國道 tisvcloud、新北）的對應表和品質規則（國道沒有 ErrorDiags）
4. 能代表路線旅行時間的資料（例如發布路段的 TravelSpeed 或 eTag），否則無法給選路建議

  - 駕駛：只看當前塞車熱點和資料時間，不做路線推薦，直到有旅行時間資料為止。
